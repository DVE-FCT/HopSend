# Git 工作流与中文提交规范

## 1. 仓库与分支

- origin：git@github.com:DVE-FCT/HopSend.git。
- 主分支：main，只接受已验证的 PR 集成结果。
- 工作分支：test/<阶段>-<英文短主题>，例如 test/p1.2-durable-resume。
- 每个阶段从最新 origin/main 创建工作分支；一个阶段结束后另建下一阶段分支。
- 不在 main 上直接开发、提交、强推或绕过 PR。
- 修改任何文件前先检查 `git status --short`、`git branch --show-current` 和 `git worktree list`。main 是只读集成基线；发现已有差异时先备份，再带入测试分支，不能先清掉改动。

工作树干净时，开始新阶段：

```powershell
git fetch origin --prune
git switch -c test/p2.15-remote-browser origin/main
```

已有 main 未提交改动时，先保存仓库外的二进制差异备份；最新 main 与当前基线兼容时，可用上述 switch 带入新分支。存在基线变化或冲突时，在独立工作树按语义迁移并验证；不要硬重置 main、强制 checkout 或将未完成工作随便提交。

## 2. 统一中文提交

格式：`类型(阶段): 中文动作与结果`。括号、冒号使用半角，冒号后保留一个空格。

| 类型 | 用途 | 示例 |
|---|---|---|
| 功能 | 新增可用能力 | 功能(P0.2): 完成密钥认证与文件范围读取 |
| 修复 | 修复已知错误 | 修复(P1.2): 修正重启后分块确认状态 |
| 重构 | 保持行为的职责调整 | 重构(P1.3): 分离任务取消与节点连接管理 |
| 测试 | 增加真实验证 | 测试(P3.2): 覆盖节点掉线后的分块重分配 |
| 文档 | 规划、说明和验收记录 | 文档(S0): 建立工程基线与阶段验收规范 |
| 构建 | 工具链、打包、流水线 | 构建(P4.2): 归集三个程序的发布产物 |
| 维护 | 必要仓库维护与集成 | 维护(P1.2): 集成主分支并验证恢复流程 |

阶段交付在提交前一并整理功能、测试、文档与验收证据，优先形成一个完整的阶段提交；避免把说明排版等琐碎变更单独推送。CI 若暴露真实问题，先在测试分支修正并完整验证，不绕过检查。已推送历史的回退或重整以用户明确要求为准。

阶段可使用 S0 或 P0～P4 及其子阶段，例如 P0.1。提交正文说明交付、验证命令与结果、未覆盖范围；标题和正文都不要写没有证据的“全面通过”。
PR 标题沿用相同规范。阶段功能提交与合并提交必须区分：功能提交描述交付结果；保留 merge commit 时统一为 `维护(阶段): 合并 test/<阶段>-<主题> 至 main`，例如 `维护(P2.6): 合并 test/p2.6-desktop-usability 至 main`。正文关联 PR、已验证 HEAD 与集成结果，不重复功能标题。使用 `git log --first-parent` 看阶段边界，`git log --merges` 查集成。不为统一消息改写已合并历史。MIT LICENSE 沿用远端内容。

## 3. 阶段执行顺序

```text
拉取远端 main
→ 创建阶段 test 分支
→ 实现本阶段
→ 执行检查并保存验收记录
→ 检查暂存差异
→ 规范中文提交
→ 推送 test 分支
→ 创建 PR
→ 集成最新 main，处理冲突
→ 对最终集成结果重新验证
→ PR 合并至 main
→ fetch 回读、核对主分支并复验
```

上面是所有阶段的当前流程。阶段编号、真实状态和未来步骤见 [阶段规划](04-roadmap.md)与[后续实施计划](23-next-stage-plan.md)；S0 的首次拉取限制仅为历史记录。

## 4. 冲突处理

1. 保存现有通过验证的阶段提交，fetch 最新远端状态。
2. 仍在 test 分支，用 `git merge --no-commit --no-ff origin/main` 准备集成；已包含最新 main 时无需额外合并。
3. 有冲突时逐文件核对双方修改的行为和契约，不能机械全选 ours/theirs。
4. 所有冲突解决并暂存后，对合并后的实际文件重新运行本阶段验证和必要回归。
5. 验证通过再创建中文集成提交，推送 test 分支并刷新 PR。
6. 使用 GitHub PR 的合并结果进入 main；合并前核对当前测试分支 HEAD 与已验证提交一致。
7. 若 main 又有更新，重新集成并复验。合并后再次回读实际远端提交。

不为了让 PR 显示绿色而删除失败测试或覆盖无关改动。合并后的回归失败应立刻按测试分支流程修复，并准确记录状态。

## 5. 本地约束

`.githooks/pre-commit` 阻止在 main 或非 test 分支提交，`.githooks/commit-msg` 检查标题格式，`.githooks/pre-push` 阻止直接推送 main。

启用方式：

```powershell
git config core.hooksPath .githooks
git config commit.template .gitmessage
```

Git 本地钩子不是服务端保护，其他克隆需要同样启用；不会自动运行全部业务测试。每个阶段仍需保存真实验收证据。
后续可在 GitHub 设置中启用 main 的 PR 必须检查与保护规则，本阶段不宣称服务端保护已配置。

S0 合并后在 main 进行只读回归时，可对基线检查加 `-AllowMainReadOnly`，仅允许检查器读取主分支，不解除提交和推送钩子的限制。

## 6. 工作树、stash 与未完成阶段

Git worktree 具有各自的文件和索引，但 refs、对象库与 stash 列表共用。看到另一工作树的 stash 是正常 Git 行为，不代表内容被放进 main。工作树负责隔离改动，stash 不负责长期保存或按工作树隔离。

临时集成需要 stash 时，记录对象 ID、所属工作树、基线、是否包含未跟踪文件及恢复结果，使用 apply 并先保留原对象；集成通过且等价验证后才 drop。不能在 P2.8 已恢复的文件上再次 pop 老快照，以免重复应用或丢掉后续修复。

跨天未完成工作继续留在专属工作树；需要稳妥备份时，将明确的快照引用归档到仓库外的原生 Git bundle，并验证 `git bundle verify`、`git bundle list-heads`、独立仓库读取快照文件及清单 SHA-256。bundle 必须包含未跟踪源码，不能只导出 tracked diff。备份可能含私密配置，按本机资料保管，不上传远端。仅有 bundle verify 不能证明工作树包含所有内容，还需逐文件比较。

既有“只在可验证阶段完成后提交”的要求继续生效。不要加 WIP 前缀、绕过 commit-msg 钩子，或在未验收阶段创建伪完成提交；也不为美化图形擅自 amend/rebase 已推送历史。

清理 stash 的顺序：

1. 按 `git stash list --format='%gd %H %gs'` 记录准确对象 ID，不凭名称判断重复。
2. 验证可恢复备份；跟踪差异和 stash 的第三父提交（若有未跟踪内容）都须保存。
3. 对 UI 快照，将其补丁施加到目标基线的临时索引，比较树内容与已验证结果；对仍活动的 P2.8，保留最新工作树快照及差异清单。
4. drop 前重读该索引的对象 ID，只有与计划一致才执行。编号会在每次删除后变化，禁止照旧编号批量删除。
5. 再次核对当前所有工作树差异、未跟踪文件和 HEAD，验证未知内容未丢失；清理报告保存在仓库外，不把个人工作区资料提交到源码。

清掉 stash 列表不是删除其唯一副本。需要恢复时，先在新的隔离目录初始化仓库，按归档清单从 bundle 取回原快照引用，读取或比较文件后再迁移；不要直接覆盖正在进行的工作。

## 7. 合并后的分支生命周期

通常保留 main 与最近一次阶段测试分支；开发期间允许额外活动阶段。P2.8 有未关闭工作，必须保留其分支和工作树，不能为了只剩两条分支而删除。

删除更早测试分支前，先 fetch，确认其提交被实际 origin/main 包含，检查 PR 为 MERGED、所需 CI/回读复验完成，再检查是否被其他工作树占用、是否有未保存工作。干净旧工作树可以先切到 detached 的已验证主分支；有修改时保留。远端和本地分别清理，不使用强制 `branch -D` 处理未知差异。

```powershell
git fetch origin --prune
git worktree list
git merge-base --is-ancestor test/p2.13-trust-rotation origin/main
# 只有上一步退出码为0、PR/复验已核对且工作树未占用时才执行：
git branch -d test/p2.13-trust-rotation
git push origin --delete test/p2.13-trust-rotation
```

PR 合并后 main 只允许 fast-forward 到远端真实合并提交；核对本地状态干净。保留一个完整阶段提交与一个独立标题的 merge commit 是当前策略，不是重复交付；用 `git log --first-parent` 看阶段边界。

## 8. 产物与运行资料

构建和临时测试资料留在忽略目录，源码不得含私钥/Token/实际 DB。使用小型可重复样本，必要的大文件验证后记录种子、长度、哈希和结果，再检查是否有任务依赖后清理。分发一般保留最新版与上一版，存在直接引用的版本先迁移入口或继续保留。凭据版本和活跃任务暂存不按文件年龄自动清除。

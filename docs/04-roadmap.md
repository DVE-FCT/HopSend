# 阶段规划与可验证交付

更新日期：2026-11-25。S0～P2.7、P2.9～P2.12 已合并。P2.7 已完成 3×3×3 单源实测及参数依据，见 [P2.7 验收](validation/P2.7.md)。P2.8 在独立工作分支继续验收，尚未合并；P2.11 已交付真正的桌面四步配对。P2.12 补齐连接闭环，P2.13 实现显式信任版本轮换，逐项状态与证据见下表。多节点调度和机器级安装服务尚未交付。

基础连通的代码与本机协议验收覆盖 P0.1～P0.3。两台 Windows 的早期局域网直连与 SSH 隧道记录见 docs/validation/P0.2-device.md；独立 HTTPS 和大文件见 P1.1；不同网络与自动恢复见 P1.3，网络路径据实际观察区分直连和中继。

每个子阶段都是可独立验收、提交、推送和发起 PR 的单位。不能仅因“文件已创建”就把业务能力写为完成。

## S0：工程和协作基线

- 接入远端 main 历史，保留 MIT 许可证并整合 Go 忽略规则。
- 在 test/s0-project-baseline 汇总已有目录、品牌、架构图和工程文档。
- 固定仓库及 Go 模块路径为 github.com/DVE-FCT/HopSend。
- 固定中文提交、测试分支、验收记录、PR、冲突处理与合并验证规则。
- 校验目录和链接、JSON 示例、资源一致性、忽略规则、提交钩子行为与 Git 差异格式。
- 本阶段不安装工具链，不宣称客户端、Agent 或传输功能已经实现。

P2.12/P2.13 可在 P2.8 外部设备验收等待期间独立推进，分阶段提交、PR、CI、合并及复验，不把尚未验证的分发和系统配置脚本混入。P2.8 的第三台干净 Windows 和源端所有者授权仍按原记录等待现场。

P2.9 目录分页可在 P2.8 的外部设备验收等待期间独立实现和合并，不把 P2.8 的未验收内容混入提交。P2.10 先独立交付发送端资料核心及 CLI，P2.8 桌面接入继续在原工作树验证；后续接收端资料生成和授权编排再迁入 Go，保留用户确认、Windows 提权与现有信任校验。

执行顺序：P2.6 → P2.7 单源基线 → P2.8 可运行分发 → P3.1 → P3.2 → P4.1 回归与故障边界 → P4.2 正式发布。P2.7 已在两设备直连矩阵比较 8/32/64 MiB 与 1/2/4 worker，保留 32 MiB / 每节点 2 块为当前保守起点，记录了 8 MiB/4 worker 更快的测量范围；全局 4 块仍待多源验证。P3.1 并发总预算同时受设备和磁盘限制。每次参数结论必须附条件，不承诺突破共享宽带上行。

目前已有 EXE/ZIP，运行本身不要求 Go/Node；缺口是可重复安装、首次配对指导、升级卸载和独立驻留。P2.8 用户登录计划任务不冒充无需登录的系统服务；标准账号和登录凭据生命周期、任务触发条件及注销后的行为必须记录。P4.2 再验收机器启动即用的服务，不悄悄提升权限。

P3.2 正确性以整块重取为基线：节点离线 → 停止并等待旧 writer → 租约失效 → 未确认块重新入队。局部缓存是减少浪费的优化候选；只有 P2.7/P3.2 的重传字节证据支持时，才另立子阶段，先设计子块哈希/持久化及版本引用，再测缓存损坏和中继节流场景。不能把未经完整块验证的前缀标成已确认块。

上传到多台接收设备采用多个独立、接收端确认的上传任务作为后续首选方案，分别授权、限流、恢复和 finalize；不将上传描述为多源下载，也暂不引入广播会话。启用前需验证多个接收端成功/失败隔离、独立哈希以及全局上传带宽预算。平台范围见 [ADR 0007](adr/0007-platform-and-distribution-scope.md)。

P4.1 的边界测试使用专用卷/虚拟机，不填满系统盘、不对用户机器实施断电；物理断电只能在隔离设备经所有者安排后记录。无法覆盖的断电硬件条件作为发布限制披露，不能用进程退出模拟宣称已覆盖物理故障。

## 每个阶段统一的完成规则

1. 范围明确：列出本阶段要实现和验收的项目，明确外部设备/网络前提。
2. 实现完成：实际入口可运行，不以模拟数据或空壳替代功能结果。
3. 验证通过：执行相关构建、逻辑/集成/端到端检查，证据写入 docs/validation/<阶段>.md。
4. 差异可审查：检查新增文件、依赖、日志脱敏和 Git diff，不混入无关变更。
5. 中文提交：类型(阶段): 中文动作与结果，仅提交本阶段通过验证的成果。
6. 推送测试分支，建立 PR；列明真实结果和仍未覆盖的场景。
7. 合并前集成最新 main；有冲突时逐项解决并重新验证集成后的代码。
8. 验证通过后由 PR 合并；回读远端 main，核对合并结果并运行相应验证。

未通过的子阶段保留在本地继续修正，不用“以后再测”跳过门槛；确实缺少外部前提时明确列为待验收，不宣称阶段完成。
重要修复可作为原阶段范围的独立可验证提交，仍遵循相同流程。

## 验证分层

- 包内逻辑测试紧邻源码；跨 SSH/SFTP、SQLite 和文件系统的验证放 tests/integration。
- 多进程、进程退出、断网恢复和桌面真实交互放 tests/e2e。
- 大文件用可重复方式生成，测试资料不进源码仓库；检查完整哈希和实际恢复范围。
- 文档与目录阶段检查链接、路径、配置、钩子和 Git 状态，不冒充业务测试。

## 后续候选

| 候选 | 触发条件与独立评估要求 |
|---|---|
| 局部块缓存 | P3.2 重传浪费显著时优先；需要可信子块和有界缓存策略，不是多源正确性的前提 |
| 自建 DERP | 确认中继可达性/吞吐为瓶颈时做运维试验；单列证书、带宽、流量成本和故障切换验收 |
| Headscale | 因控制面自主性/组织管理需要再评估；不等于 DERP，不移除软件发行、证书等其他外部依赖；迁移和回退另立 ADR |
| QUIC | 基准证实 TCP/SFTP 在长延迟/丢包场景受限后，比较端到端吞吐、CPU和运维成本；同样保留认证/版本/可靠落盘语义 |
| WebRTC | 另评浏览器互通、信令和穿透需求，不与 Headscale 或 QUIC 绑定决策 |
| 浏览器收件 | 明确轻客户端需求后再做；认证、下载发布与传输适配器范围单列 |
| 多接收端上传 | 从多个独立任务开始；需求明确后单列阶段，不改造现有 v1 为未验证的广播 API |

候选排序依据真实瓶颈和维护成本，不预先宣称某一种网络方案必然更快或优先级最高。

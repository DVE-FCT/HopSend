# P2.7：单源性能前置基线

日期：2026-11-23。分支：`test/p2.7-single-source-baseline`。基线 main：P2.6。

## 交付与环境

新增实际 CLI `benchmark`、有界矩阵/流量预算、固定种子合成文件生成脚本、原始报告与统计。复用生产 HTTPS、SFTP、SQLite 和下载引擎，没有修改传输算法来制造更高基准值。

- 接收端：Windows 11 家庭版 build 26200，i9-14900HX，32 逻辑 CPU，约 32 GiB 内存，UMIS NVMe，NTFS。后台有桌面/开发程序，不是隔离实验室负载。
- 源端：Windows 10 家庭中文版 build 19045，i5-10210U，8 逻辑 CPU；同一局域网 Wi-Fi，Windows OpenSSH，Tailscale 加密直连。标准 SSH 账号没有 CIM 权限，源盘型号与物理内存未采集，不伪造硬件细项。
- Go 1.27.4，Node 24.14.1，pnpm 11.25.0，Wails 2.17.1，应用版本 0.1.0-dev。网络开始/结束观察均 direct，Tailscale ping 观察到局域网端点；不把整个过程证明成没有抖动。
- 合成文件：192 MiB＋17 字节（201326609）；seed=20261123；两端独立生成并核验相同哈希。SHA-256：`1b6d3961e70deef5346ac486ccdc094374ce907e54e0d0c2bee002eb71ed2689`。
- 时间：北京时间 21:22:03～21:38:28。原始报告用 UTC 保存。三轮交错矩阵，共 27 次生产引擎下载，另有 SFTP 预热及 3 次对照；有效载荷共 6241124879 字节，不含协议开销与前期失败重跑。

## 实测结果

本机 SHA-256 三轮中位 1675.82 MiB/s（1477.38～1729.81）；源读取＋写盘＋每 32 MiB Sync 中位 1231.35 MiB/s（1194.64～1315.68）。这是热源/新目标测量，不是冷盘或持续写入到闪存缓存耗尽的速度。

## 参数决定

保留 **32 MiB＋每节点 2 worker** 作为当前保守起点：同一块尺寸下 2 worker 比 1 worker 的中位速度约高 25%，4 worker 没有稳定优势，且多两条连接、采样工作集更大。32 MiB 比 8 MiB 减少逻辑确认次数，2 worker 下的中位略高于 8/64 MiB。

这不是“32/2 全面最快”：8 MiB＋4 worker 本轮中位 7.65 MiB/s 更快，4 worker 的最高值也更高。P3 设置应保留有界调节，按真实设备/网络继续比较；需要时选吞吐更高的组合，而非把初值锁死。全局 4 个活动块未在多源情况下测量，仍明确标为设计预算，不能将单源成功冒充全局调度已验证。

CPU/磁盘/哈希本轮远高于约 6～8 MiB/s 的网络传输量级，未见客户端这两项成为主瓶颈。不是对源端磁盘/CPU或其他网络的普遍结论。内存来自同一进程分段采样，可能包含前序保留堆，不能解读为单任务的独占或增量内存。

## 验证与首轮问题

- `scripts/check/check-go.ps1 -StrictDoctor`：前端 TS/Vite、gofmt、vet、所有 Go 包、CLI/Agent 构建及固定工具链检查通过。
- 最终针对 benchmark/CLI/真实 HTTPS/SFTP 集成包重测通过。新增测试覆盖实际写盘/哈希、不覆盖已有目录、预算在建连前拒绝、错误内容清单拒绝、真实网络全新下载及统计排除失败样本。
- `scripts/build/build-desktop.ps1`：Wails 与配套 Agent 构建通过；本阶段不改变桌面交互。
- 工程基线与 `git diff --check` 通过；完整重复矩阵和原始结果已保存后才提交。
- 早期源端一度离线/SSH 重置，256 MiB 上传超时；改为两端按种子生成后独立核验，减少准备流量。首次 256 MiB 网络轮次因明显抖动中止，第二轮在 300 秒只读到 206143488 字节，未通过完整哈希，报告为失败，未混入成功统计。测量入口增加明确的原始读取时间上限，当前为 10 分钟；完整通过轮次缩为仍覆盖 64 MiB 四块的 192 MiB＋17 字节。

## 边界

未测冷缓存、以太网、DERP/热点性能矩阵、源端资源采样、5 GiB 持续稳态、更多物理设备或多源并发。本阶段保留可重复方法与有条件的参数依据；发布前性能回归仍按 P4.1 扩展。无 Go/Node 的新系统安装和重启登录验证属于 P2.8。

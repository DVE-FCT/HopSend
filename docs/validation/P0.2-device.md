# P0.2 两台 Windows 联调与主机密钥协商修复

日期：2026-11-23。分支：test/p0.2-windows-device-validation。
本记录使用“客户端 A / 源节点 B”代替真实账号、设备名、地址、指纹和机器目录，原始现场记录只保存在本地验证资料中。

## 真实环境与身份确认

- A：Windows 11，本工程编译的 HopSend CLI。
- B：Windows 10 build 19045、Windows OpenSSH Server、非管理员专用账号、公钥认证。
- 两端 Tailscale 在线且处于同一受控网络；实际探测显示同一局域网的 UDP 直连，初次观测延迟约 6～30 ms。
- 先采集服务器 ED25519 公钥，再逐字匹配用户从服务端提供的 SHA-256 指纹，一致后才写入本机专用 known_hosts。
- 本机私钥没有传到远端；认证时严格验证主机身份。

## 真实联调发现的问题

原客户端只设置 HostKeyCallback，使用 SSH 库默认主机算法顺序。当服务端同时提供 ECDSA/RSA/ED25519，而人工仅核对并保存 ED25519 时，客户端可能先协商其他算法，最终报 knownhosts: key mismatch。
原自动测试服务只提供一种主机密钥，没有覆盖真实 Windows OpenSSH 的多算法场景。

## 修复

- 使用固定版本 github.com/skeema/knownhosts v1.3.1 获取该目标主机在信任文件中的算法；它封装 x/crypto 的信任记录解析并支持散列主机名和证书记录。
- 将已信任算法与 ssh.SupportedAlgorithms().HostKeys 取交集，再设置 HostKeyAlgorithms。
- 仍使用主机公钥回调进行完整验证；未知主机、真实密钥变化及不受支持的旧算法不会自动放行。
- 修改真实 TCP 测试服务，同时提供 ECDSA 和 ED25519，客户端只信任 ED25519；新增散列 known_hosts 的等价验证。
- 握手超时测试同时核对 TCP 确实已接入和错误确属超时，防止被更早的主机信任拒绝误当成超时通过。

## 实际结果

| 项目 | 结果 |
|---|---|
| 人工指纹与采集到的 SSH 主机公钥 | 一致 |
| 专用账号公钥认证 | 成功 |
| HopSend 对 B 的 Windows 绝对路径执行精确 SFTP 范围读取 | 成功，使用 `/C:/…/sample.bin` 形式 |
| 独立读取三次 | 每次恰好 1,048,576 字节；范围 SHA-256 全部与用户给定值一致 |
| 原实现配合新增多算法测试服务 | 普通及散列 known_hosts 两个回归用例均复现 key mismatch，符合预期失败 |
| 修复后的格式、vet、全部 Go 测试、CLI/Agent 构建与工具链诊断 | 通过 |
| 原有未知主机、变化主机、错误用户私钥、取消、截断和范围检查 | 回归通过 |

1 MiB 的读取仅用于正确性验证，不能据此给出大文件速度或跨公网性能结论。

## P0.3 远端 Agent 补充验收

通过已认证的 SSH/SFTP 将 CLI 和 Agent 开发构建复制到 B 专用账号的唯一临时验证目录，两份二进制的 SHA-256 均核对一致。
在 B 上创建独立 TLS 身份和 API 凭据；验证服务器私钥和 Token 的 NTFS ACL 仅允许专用用户和 SYSTEM。
客户端只经已信任 SSH 取得 CA 公钥及自己的 API 凭据，并核对 CA 证书指纹；服务器私钥保持在 B。

远端 Agent 只监听回环随机端口，客户端通过 SSH 转发访问 HTTPS。真实验证了：

- health/capabilities，且不宣称未实现的上传能力。
- 只显示已授权共享，能查到 1 MiB 样例文件元数据。
- 错误凭据返回 401，未授权共享返回 404，越界路径返回 400。
- 本工程编译的 CLI agent-status 查询成功。
- 测试结束关闭 Agent 和转发，并通过远端只读查询确认该临时 Agent 已停止。

未修改 B 的系统服务、防火墙或用户组；临时验证目录保留在专用用户数据目录，私密材料没有加入代码仓库。

## 仍未验收

- 两设备处在不同公网网络时的 NAT 穿透，以及 DERP 中继的可靠性/吞吐。
- 大文件、文件夹、持久化续传、上传、多节点与桌面 UI；这些属于后续阶段。
